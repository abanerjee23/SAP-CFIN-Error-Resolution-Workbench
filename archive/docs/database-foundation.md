## Factual additions

New cases carry `workflow_version='log-only-v1'`, source manifests, a saved factual result and independent factual review status. Intake preserves separately versioned UTF-8 originals and allows unknown SAP identity/order. Queued jobs pin schema/prompts/models and source-manifest fingerprints; publication checks immutable snapshot, lease and revision bindings. Evaluation runs cannot publish an operational summary, assign an owner or satisfy human milestones.

Factual Accepted/Corrected/Insufficient reviews preserve the model result. Investigation milestones separately attribute findings, action/no-change, outcome, scope, gaps and proof. Actual corrective work retains authority checks; successful reprocessing establishes explicit chronology and validation records human expected/observed comparisons. Context owner rules use explicit system/interface/company metadata with membership, version and expiry guards. Existing cause rules retain their original meaning.

Machine-reader scope, credential revocation and bounded read audit are additional access boundaries. Case/source reads retain independent workspace/source authorization and immutable versions. A machine identity does not inherit a portal or SAP user's permissions.

The historical schema description below documents retained legacy contracts. It must not be applied as diagnostic prerequisites to factual cases.

## Retained legacy records and relationships

| Record | Installed identity and relationship rules |
| --- | --- |
| Workspace / membership | Membership uses actual Auth user UUID plus workspace UUID; one account may hold several explicitly listed demo roles. Browser users cannot grant roles. |
| Case | UUID for the application record; complete business identity is unique within workspace across source system/client/company/year/document and target system/client/interface. Business identifiers are text and preserve leading zeros. Incomplete identity remains provisional. Explicitly linked provisional aliases preserve their intake/audit history and are excluded from normal distinct-case totals. |
| Attempt | Unique external attempt key within the case; positive processing order starting at 1 and processing time are distinct from receipt time. Current-attempt FK must point to that same case/workspace. Ordering ambiguities need human review rather than a uniqueness constraint that guesses order. |
| Evidence version | Immutable source/version text identifiers, SHA-256, provenance, observation/uploader/storage times and private object path. Object paths begin with workspace UUID. Current input files are each bounded to 1 MiB; complete input packs and individual proof uploads are bounded to 10 MiB. Original bytes live in private Storage. |
| Intake / input control | One delivery key per workspace and a payload fingerprint. Original evidence is bound to the exact case/attempt. The guarded RPC compares content and returns an existing intake or rejects a conflicting delivery. The backend verifies stored bytes before registration/queueing. General MD-01/MAP-01 packs use declared source/version bindings; provisional identity completion, attempt-order review and alias linking require authorised, version-checked actions and reasons. |
| Run / job | Immutable input snapshot/hash, exact saved source/review versions and actual requester. One active operational run per case/snapshot and one job per run; isolated evaluation repeats are tracked separately. The worker restores nine saved inputs and uses database leases/heartbeats. Earlier live SQL verified singleton claims, replacement/expired lease fencing, late receipt idempotency, historical input revisions and atomic current publication; process restart recovery and broader concurrency remain open. |
| Validated stage / preparation reuse | Checkpoints bind the actual run/stage to validated structured output. A reused preparation records its source run and must match the same workspace/case/attempt, exact inputs/reviews/context, prompt version, preparation model and effort. Evaluation and operational reuse remain separate. Invalidated checkpoints cannot silently resume; changed snapshots and expired leases prevent stale promotion. |
| Assignment / notification | Versioned assignment tied to the case and actual member; notification key is unique per event/assignment. Notifications are explicitly simulated and have durable leases/retry records. Only successful delivery for the latest assignment can advance a still-created case to owner-notified; obsolete deliveries remain historical. |
| Reviewed default owner — legacy coupling | Immutable, versioned process-owner rules bind an actual member and matching owner role to an exact category, target/client, company, chart and interface, with a reason and review expiry. Only a current successful supported diagnosis can apply an active matching rule automatically; model/file labels cannot configure rules, and evaluations cannot assign owners. A revised factual summary cannot satisfy this diagnostic gate; factual ownership instead uses the separate context-rule branch. |
| Human review | Decision, rationale where required, separate cause confirmation, actual actor/role/time and the exact run from the same case. Accepting wording alone does not establish human confirmation. |
| Milestone / proof | Milestone records case/attempt/cycle, actor/time and explicit human confirmation. Linked evidence must belong to the same case. Reusing earlier evidence requires a new human attestation of applicability to the current attempt/cycle. Attaching a file alone never satisfies a milestone. |
| Resolution | Versioned per case/cycle and tied to the attempt, with required cause/evidence or gaps, correction, scope, outcome and resolver. Reuse begins Pending review; the operational resolution action cannot publish learned knowledge. |
| Guidance / reference review — legacy coupling | Exact saved evidence version, kind/scope, decision, actual actor/role/time and rationale. Mapping review requires its authorised role. Draft bytes remain unchanged; authenticated reviews form an audit overlay. Eligibility is checked before routing and actionable use. No actual approvals have been recorded by software tests. These references are not required inputs to the agreed log-only summary. |
| Proof applicability | A separate attestation links saved proof to the milestone's current attempt/work cycle; reusing earlier proof requires an explicit human reason. Server-generated fictional result observations remain labelled synthetic and require an actual authenticated action. |
| Stage call / budget | Versioned known pricing, maximum input/output bounds, lease-bound reservation and recorded usage/cost. Unknown usage retains the reservation. Operational analysis, saved-case evaluations and Agent 4 share the maximum US$10 UTC-month allowance; each run is bounded by US$1, with lower configured caps enforced. Reconciliation precedes publication. Earlier rollback-only SQL verified smaller caps, duplicate-dispatch denial, unknown-usage retention and confirmed not-sent release without calling a model; new shared-budget/race behaviour still needs thorough live testing. |
| Overview snapshot / member / group / run | An actor-scoped, immutable five-minute snapshot saves exact case membership/versions, distinct known-case metrics, separate provisional/attempt totals and drilldown group IDs. Reads recheck membership and flag changed/expired snapshots. Charts remain available with paid mode disabled. Explicit Agent 4 explanations use read-only tools, bounded Sol/medium execution, the shared model slot and a durable budget reservation. |
| Knowledge version / feedback | Drafts are Pending review by default and bind a real resolution, immutable content version, scope and applicability. PostgreSQL text/context matching plus local deterministic concept hashing rank only currently approved accessible versions; no learned embedding/provider call is used. Human feedback remains a reviewed proposal and cannot publish guidance automatically. |
| Publication policy / evaluation attestation — legacy coupling | Process owners must explicitly configure quality criteria and review actual model-quality evidence for the exact candidate version. Confirmed cause, complete applicable successful validation and explicit review also gate publication. Software scores and queued jobs cannot satisfy these prerequisites; no actual approved learned lesson is claimed. These diagnosis-era prerequisites need adaptation for the revised feedback loop; they are not gates for generating a factual summary. |
| Run knowledge source | Each analysis saves the exact retrieved knowledge IDs/versions and revalidates them before actionable promotion. Withdrawal removes retrieval eligibility immediately, marks affected open cases for refresh and blocks in-flight use, while preserving saved history. This retained legacy retrieval feeds Agent 2; the factual branch separately loads relevant case/log content for Agent 3 only. |
| Evaluation batch / run | Explicitly selected current saved case snapshots, model IDs, effort and repeat IDs are persisted separately with `evaluation_only=true`. The worker applies normal leases, checkpoints and shared budgets, but these outputs cannot promote operational cases, assign owners, approve references or complete human milestones. Legacy evaluation jobs execute the earlier stages; version-pinned factual jobs use the dedicated factual report path. |
| Activity | Append-oriented event record with actual actor/role, old/new values, time and reason; workspace events may have no case but still require a valid workspace. |

Database record UUIDs are internal identities. `synthetic-cfin-demo` in the local fixture is a fixture workspace label, not an Auth membership or cloud UUID. Intake binds it to the already authorised workspace; it cannot grant access. External attempt/source keys stay distinct from row UUIDs. Agent outputs cannot set database actors, roles, priority, case version or membership.

The installed lifecycle, diagnosis, validation and reuse fields use separate stable machine enums. These are existing storage contracts; revised factual summaries must not be relabelled as diagnoses merely to fit them. Priority stays `P1` Low, `P2` Medium, `P3` High; Resolved is derived. Human RPCs require the expected case/review version and save audit records in the same transaction. Live SQL confirmed stale case-version and unheld-role rejection. Actual human review/milestone actions and broader race tests remain separate checkpoints.

## Access, persistence and observability

Authenticated roles have SELECT table grants plus only the guarded human RPCs. Membership policies scope operational reads; membership rows are self-only. Anonymous roles receive no operational grants. Storage reads require preserved linked evidence and current membership. Browser roles cannot directly upload or mutate records. The separate service gateway verifies bytes and invokes service-only registration/worker RPCs; its credential never enters the browser or model input.

The implemented schema includes backlog snapshots, reviewed-history publication/search, saved-case evaluations, durable stage recovery and reviewed owner defaults. Arize AI (Arize AX) handles both AI evaluations and observability in the configured Default Space and `cfin-document-error-analysis` project. `OpenAIAgentsInstrumentor` automatically captures SDK activity; no manual operational traces are created. Its five-span automatic smoke and twelve-record/96-score native software experiment are independently API-verified, with no real provider/judge calls. Galileo and Promptfoo are retired from active paths; retained results are historical evidence only. Operational spans are buffered until business commit, and transport acceptance is distinct from independent server/UI visibility. A successful traced operational analysis remains open. Business audit, durable stage records and budgets stay in Postgres.

## Integration work for the agreed design

1. Support supplied-log intake and new extraction/selection/summary snapshots without mandatory external reference packs or diagnosis fields.
2. Retain the complete original, every supplied view/attachment and source locations. Embedding all supplied evidence in the revised case needs UI integration; private storage alone does not establish that experience.
3. Supply authorised reviewed history to Agent 3 only, with separate historical citations and exact source/version registration. Preserve access and withdrawal controls. Historical findings cannot establish the current cause or become recommended fixes.
4. Keep manual ownership and explicit unassigned states while adapting automatic routing without inferred causes. Do not fabricate a diagnosis to satisfy existing default-owner rules.
5. Support mandatory meaningful human updates: corrections, investigation findings, unresolved issues and outcomes. Preserve existing audit/review records and adapt diagnosis-dependent publication prerequisites deliberately; accepted feedback must not publish itself automatically.
6. Version the new stage and evaluation contracts so earlier outputs cannot be reused as revised outputs solely because the model IDs match. Preserve budget reservations, leases and immutable inputs.

No migration implementing those changes has been applied. This work adds neither SAP integration nor a diagnostic rules engine. Ordinary permission, source/reference and version checks remain application responsibilities; structural validity does not guarantee extraction completeness or semantic accuracy.
